# 记牌器BETA 与正式版发布流程

流程按用户最新决定执行。项目级约束见根目录 [AGENTS.md](../../AGENTS.md)。本轮正式版 `v0.2.27` / versionCode 29 已发布；签名清单、完整生产下载和安装身份已验证，新增手机安装按用户本轮要求豁免。

| 项目 | 记牌器BETA | 记牌器（正式版） |
| --- | --- | --- |
| 包名 | `com.cyotun.jpq.candidate`，沿用已有测试数据 | `com.cyotun.jpq` |
| 用途 | 新功能、识别修复、性能优化的独立开发与验收 | 已发布功能的日常使用 |
| 更新 | 当前不读取或安装正式通道 | `jpq` 的签名正式清单和安装包 |
| 安装关系 | 可与正式版共存 | 不能被 BETA 包覆盖 |

“candidate”仅是历史包名、Gradle 构建类型和源码开关，不代表用户可见名称。旧证据文件名不改写。

正式版 API 37 及以上启用 `APP_TASK` 单应用采集，旧系统使用 `DISPLAY` 整屏采集；两者均保留系统屏幕共享授权。能力开关 `SINGLE_APP_CAPTURE_ENABLED` 不得与 `SINGLE_APP_CAPTURE_CANDIDATE` 的 BETA 身份混为一谈。BETA 与正式版继续使用独立包名、应用数据和更新通道。正式版不承担日常测试；不维护常驻 BETA 开发分支，确有测试需求时临时构建独立 BETA。

## 开发到验收

1. 先确认正式回滚 APK、哈希、证书和源码标签可用，再在隔离的开发工作区制作 BETA。
2. 完成代码 review、核心与宿主回归、静态检查及对应的电脑模拟。记录失败与修复，不把跳过记为通过。
3. 通常继续进行必要真机检查和用户实战验收。若用户明确豁免某轮步骤，记录为“豁免”，不能记成通过、设备兼容性结论或实战验收。对局由用户操作；采集期间只读取证据。
4. 本轮 v0.2.27 用户明确豁免新增真机及实战验收。电脑回归中 19 个正常局来源共 28,442 帧、681 个事件；另有一个 3,521 帧中断来源仍未核实，不能计为通过。最终测试总数以发布记录为准。
5. 本轮 BETA 工作分支归并至 main 前先创建 archive 标签，再删除该开发分支。标签保留追溯；以后新功能仍按 BETA 流程开发，可按需临时建分支，不做日常 BETA 分支维护。

## 提升到正式版本

默认不得将未获验收或明确豁免的 BETA 改动直接混入正式 APK。本轮提升范围按 2026-11-12 用户明确授权处理，详细限制见发布记录。必要时从上一个正式标签创建 `codex/` 发布分支，只合入已验收改动，复跑相关完整回归。

正式版保持包名、安装证书和数据结构兼容，`versionCode` 严格增加。构建后核对真实 APK 包名、版本、minSdk、证书和 SHA-256。使用 `tools/release/package.mjs` 生成 Ed25519 签名清单和不可变分片；此脚本会拒绝 BETA 包名。

先在本地验证服务和分片下载，再部署专用 `jpq-release-store`。通过 `jpq` 的生产入口验证签名清单、HEAD、跨片 Range、整包哈希和安装身份后，更新发布文档和源码标签。服务仅用于更新，不上传私人对局资料。

正式 APP 每日自动检查、空闲时在 Wi-Fi 下载；用户也可通过设置一级菜单右侧的更新按钮检查和下载。安装仍使用 Android 系统确认，对局期间不下载或发起安装。发布记录分别记录服务接口、签名清单、下载完整性、客户端校验和实际手机安装结果。通常需完成实际安装检查；本轮明确豁免时不得冒称安装通过，也不得以该豁免自动放宽未来版本。

## 回滚

每版保留上一正式 APK、源码标签、签名身份和部署版本。BETA 失败时停止 BETA 共享后使用仍共存的正式 APP；不卸载或清空正式数据。已发布正式版的代码回退使用更高 `versionCode`，不让 Android 自动降级。

当前正式版本为 `v0.2.27` / versionCode 29，线上已发布。旧正式版本 `v0.2.26` / 28 的服务器恢复记录仅为历史依据，见 [更新服务验证](official-updates-20261024.md)。
