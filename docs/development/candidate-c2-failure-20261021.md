# C2 真实整局失败与 C3 诊断进展

2026-10-22 后续：[C3 手机非对局检查](phone-c3-non-game-20261022.md) 已完成，新增一次真实手机专用 GLES2 任务错位的自动恢复证据。下文保留 10 月 21 日当时的证据和未验证标记；不将专用画面恢复等同于腾讯游戏整局验收。

## 结论

用户反馈全程没有记牌，本轮判定失败。C2 仍不具备作为单应用 Beta 交付实战的条件。稳定版 `v0.2.26`、独立安装包、回滚源代码包和稳定更新服务器均未改动。原有浮窗/通知隔离试验只能证明相应非对局场景的像素隔离，不能抵销本次失败。

## 完整证据和记录边界

正常停止候选共享并确认系统投影为 null 后，已取回完整原始诊断 ZIP。会话 `1792518193025-50342ffc` 共 105,930 条帧记录，其中 105,916 条为 2608×1200、FULL/CPU 的横屏帧；105,728 条场景 UNKNOWN，202 条 TABLE。记账事件为 0，观察器一直未完成开局绑定。

电脑只读采集器有 3,600 秒时限，保存了其中 18,591 帧后到期，不能代表完整长会话。统计结论来自手机完整 ZIP，而非截断的电脑摘要。未以截图或额外录屏作为这局识别输入，对局期间未操作游戏、改设置或重启共享。

本机私人证据位于 `captures/phone/candidate-c2-failed-live-20261021-r1/`，不提交 GitHub、不上传服务器。原 ZIP 为 224,581,535 bytes，提取的本会话 trace 为 216,048,384 bytes。原会话的诊断图片缺失：旧图片保存条件要求已识别场景或已绑定牌局，从开局就 UNKNOWN 的会话没有留下同时间戳图片。

## 已发现的异常

- 失败会话的采集和 CPU 模型推理持续运行，但 105,714 帧没有检测到任何牌。偶发检测均聚集在画布底部，不能形成有效手牌。
- 在两轮具有同时间戳原始图/模型输入的正常大厅取样中，金币文字位于顶部中间；失败会话中同一金币文字长期落在左下方，报告的画布宽高仍然是正常值。这是内容布局异常的证据。
- 结束后重新授权的结果页取样中，原始图、转换图和模型输入确实为完整正常结果页。只能说明新会话此时可正确采集，不能反推失败会话的实际内容。
- 因失败会话没有对应原始图，尚不能确认是任务选择器/最近任务变换、游戏任务变化还是其他厂商系统组合问题。禁止凭坐标推测直接裁剪/拉伸输入，或下调识别阈值掩盖问题。

## 模拟器验证方法

使用官方 Android 17/API 37 x86_64 模拟器。测试 APK 独立显示现有四张真实牌面测试图，经普通系统单应用授权、真实候选 CaptureService、ImageReader 和 FULL 模型，检查同一原始图像时间戳的检测结果。手牌张数和各家出牌按既有 golden 预期校验；不是把图片直接送入模型绕过采集，也不是整局录像回放。

辅助画面分别通过 ImageView、独立 SurfaceView 和 GLES2 GLSurfaceView 绘制，覆盖横竖屏、最近任务返回、Surface/GL context 替换等生命周期。角落 8×8 动态标记让系统持续提交真实缓冲，不参与牌面识别。真实记牌条保持可见；仅选择器目标 UID、到帧、图片有颜色均不能单独判通过。每轮最后正常停止并验证投影回到 null。测试图片只进入独立测试辅助 APK，不进入记牌器安装包。

测试工具早期的就绪、静态画面只有两帧、异步图片写入和系统投影初始化时序问题均保留失败记录。模拟器原始图诊断比手机慢，原始图完成等待上限仅在模拟器 fixture 模式增加，未改变生产识别规则或手机取样上限。

这组测试验证采集到模型和座位分区，不能证明完整真实牌局记账成功，也不能证明澎湃系统上的布局故障已经修复。

## 已复现的布局错误

在模拟器 case4 的 SurfaceView 重建与最近任务返回组合中，已复现真实候选管线故障：物理屏幕完整显示 1560×720 的牌面，原始 ImageReader 同样报告 1560×720，但实际内容被缩小到约 46.15%，移到左下方约 y=614 的位置，大部分牌面在采集边界之外。转换前后像素一致，模型输入也绑定同一原始图像时间戳，识别手牌为 0。这是实际失败记录，不是测试工具等待超时。

证据：`captures/emulator/card-fixture-20261021/case4-landscape-surface-True-True-20261021T005553Z/`。普通 ImageView、竖屏转横屏/最近任务、SurfaceView 普通绘制，以及单独 SurfaceView 重建、单独最近任务返回均通过；组合场景失败。此触发具有时序因素，尚不能仅因个别重跑成功就宣布已修复。

这个模拟器错误与手机会话金币文字落在左下方的日志特征接近，但手机原会话缺原始图，仍不能声称已证明两者必为同一系统缺陷。通过公开 `setSurface(null)` / 新 Surface 重挂方式，已有一次有效的同会话恢复实验：先验证实际 hand=0、scene=UNKNOWN，再分离消费 Surface，350ms 后给原 VirtualDisplay 重新附加同尺寸 ImageReader。原始探针两帧的 FULL 检测重新得到 25 张手牌和正确出牌区域，随后 34 条生产识别帧全部匹配 golden。证据为 `case4-landscape-surface-True-True-refreshTrue-20261021T011937Z`。没有创建第二个投影或复用授权 token，没有对图像做猜测性裁剪、拉伸。

此组合故障并非每次出现。前四次恢复试验没有遇到前置损坏画面，未触发重挂，均不得算恢复成功。延长模拟器系统转场后，前两次仍没有触发，第三次才取得上述有效证据。模拟器三项动画设置已恢复原值；全部原始试验保留。不把未触发缺陷的重跑包装成修复证据。

## C3 自动恢复边界

候选版接入同一种公开 API 方法，仅 APP_TASK、完整横屏、尚无已绑定牌局的 WAITING 状态，场景 UNKNOWN 且手牌为 0 时，稀疏采样 512 个像素。80%–99% 近黑像素连续持续 3 秒走快速恢复。因为手机失败会话缺少源图，不能假定都符合黑边阈值；另外加入连续 8 秒完全识别不到开局的兜底。全黑的空画面不走 3 秒快路，但可触发 8 秒兜底。两条路径共享每会话最多两次请求、相隔至少 15 秒的预算，任何不符合开局条件的帧都打断持续区间。预算耗尽后不再采样。诊断开关不控制恢复逻辑。

服务在与牌局提交相同的 sessionGuard 下重新检查 WAITING/无 roundId，并递增可见性 epoch，防止排队请求跨入已开始记牌的牌局。延迟重挂受会话 generation、原 reader/display 身份保护，停止时移除延迟动作。旧 reader 在采集线程完成当前复制后关闭。识别中的旧 epoch 帧不能提交到新画面。

ACTIVE、SELF_FINISHED、RECOVERING 或已经绑定 roundId 的局不执行这项开局恢复；稳定版 DISPLAY 路径不启用。模型、输入实际尺寸、出牌归属和账本保持原规则。候选中另有严格限制模拟器的显式 LAB 动作，供前置故障/手动重挂对照使用，正式手机没有该入口。仍需手机非对局验证，不能直接以模拟器手动恢复实验宣布手机版可实战。

每个恢复请求记录触发原因与源帧；服务另外记录同一 generation/recoveryId 的 `detached → reattached → first_frame`。首个新帧带原始图片时间戳，FULL 模型记录带 visibilityEpoch。测试同时要求阶段顺序、可见性 epoch 前进和重挂后真正处理到新模型帧，避免把发出恢复请求当成恢复成功。受控 UNKNOWN 画面可以验证自动服务链路和预算；它不等同于自然几何故障被自动修复。

公开依据：[VirtualDisplay Surface 替换](https://developer.android.com/reference/android/hardware/display/VirtualDisplay)、[MediaProjection 尺寸与会话限制](https://developer.android.com/media/grow/media-projection)。公开 API 支持替换，不保证所有厂商系统具有相同恢复行为。

## 计时隔离与测试环境复核

收尾复核发现：竖屏/不完整帧提前返回，以及可见性 epoch 改变时，开局策略可能沿用变化前的时间区间。已在这两处打断持续区间；预算和冷却不清零，旧画面等待时间不能被新画面继承。该变更后重新构建并重跑同一批采集检查。

晚间冷启动复测出现过模拟器 System UI 和辅助程序无响应，均发生在正常共享授权前，不算生产识别通过。宿主机仅剩约 230 MB 空闲内存时，先关闭模拟器完成构建；后发现 host GPU 模式的模拟器实际占用约 5.3 GiB，改为 SwiftShader/GLES（禁用 Vulkan）与 4 个虚拟核心后，宿主可用内存恢复到约 3.2 GiB。启动参数请求 2 GiB guest RAM，但本版本模拟器日志明确将其提高到最低 4 GiB；不能把参数当成实际内存。构建与模拟器测试随后分开执行。此变化只是电脑测试资源调整，不是手机节电测量。

另补强授权脚本：不再依赖点击后的固定 500ms 加单次读取；有界等待标准 APP-only Next 与专用辅助任务。每次 UI 导出使用独立文件名，确认新 dump 成功后才读取，并移除远端临时文件，防止失败导出留下旧 XML。实际目标 task/UID、图片时间戳、模型和停止检查保持不变。系统窗口延迟/无响应的失败记录全部保留，不能通过放宽牌面断言消除它们。

原始探针与生产帧关联的测试边界另作修正：一次配对原图比稳定区间开始早 78ms，但同一时间戳的 FULL 生产帧和所有 33 条区间内帧均正确。测试现在额外校验所有配对生产帧，仍独立要求至少 10 条区间内帧全部符合 golden，不把区间外配对帧凑入最低数量。随后一次 GLES2 软件渲染测试的 33 条区间帧正确，但三张原图全被最新帧队列退役，没有留下模型配对；该轮仍判失败。GLES2 辅助画面的角落时钟改为约 1fps，为原图/模型配对留下处理时间；ImageView/Canvas 仍为 4fps。正式应用采样频率和队列策略没有因此改变，这些辅助画面不用于吞吐量或节电结论。

## 降耗后续候选

已只读核对生产路径：33ms 采集门限后，即使模型线程忙，仍转换并复制整帧，再由 LatestFrameDispatcher 退役旧待处理帧。FrameBitmapConverter 的可复用 bitmap 还会再绘制到 CaptureFrameProducer 独占的池化 bitmap。直接写入独占缓冲可能减少一次全帧复制，但必须完整保留行步长、像素步长、crop、alpha、跨线程所有权和停止清理规则。

后续还可比较 CPU 推理 2/4 线程与关闭诊断时的热路径开销。现有检测器已经具有精确模型输入缓存，不需要重复加入近似图像哈希。当前 C3 未实现上述优化，以免与开局采集修复混合变因。收益需要同条件、关闭诊断、断开充电的真机测量；模拟器帧率和执行时间不能替代温升/耗电结论。
