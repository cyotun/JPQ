# 程序逻辑手册 · v0.2.27

2026-11-12 按当前源码核对。本文解释**如何处理、何时提交、失败时保留什么**，供新会话定位修改。产品要求见 [需求追踪](../requirements-traceability.md) 和 [当前规格](../design/current-spec.md)，类文件导航见 [架构](architecture.md)，不可放宽的约束见 [恢复不变量](recognition-recovery-invariants.md)。所有文件路径以 `JPQ/` 为根；本次补文档没有修改生产逻辑或重新验证手机。

## 1. 对象和来源，不能混用

| 名称 / 源码 | 含义 | 不能当作什么 |
| --- | --- | --- |
| `Card`、`Rank`、`Suit`，core `Cards.kt` | 点数+颜色/花色；普通牌可为精确四花色，也可仅RED/BLACK；王为NONE | 主检测通常只给红黑，不能当全部实体花色已知 |
| `PlayGlyph`、`GlyphBox` | 直接观测牌及其归一化几何槽位 | 单靠字符串相同不能判定同一物理事件 |
| `ObservedPlay` / `TableFrame`，`Observation.kt` | 一帧场景、本手、分家出牌、是否真正可观察、数量/过牌/完成来源等提案 | 不是已确认事件；未观察到不等于空桌或不出 |
| `PlayEvent(roundId,eventId,sequence,seat,cards)` | 成功提交后带局、唯一身份和顺序的账本记录 | 不能把结算明牌、贡牌、自动三游或队友余牌追加为已出牌 |
| `RemainingHandCount` | 独立读到的某家剩余数量及原采集时间 | 不是具体牌面，也不是从账本算出的数；不能靠数量猜缺牌 |
| `StraightFlushEvidenceTracker` 的实体/花色注释 | 对同一初手/事件/队友余牌的附加证据，可能保留多个分配 | 桌面显示的替代点数 `renderedCards` 不必等于逢人配真实身份 |
| 显示缓存与候选金字 | 最近确认显示或保守候选范围 | 不能回填账本、充作OCR来源或证明本帧没有遗漏 |

座位固定为 `SELF=自己`、`PREVIOUS=上`、`OPPOSITE=对`、`NEXT=下`；腾讯当前横屏布局对应自己下方、上家左、对家正上、下家右。归属由 `PlayOwnership` 对整组几何分配，不按昵称或每张牌独立猜座位。进入队友视角后，底部展示区属于对家余牌，**不会把所有座位重新旋转命名**。新游戏布局须另作适配。

## 2. 从启动到停止

1. `MainActivity` 检查可用游戏组合和悬浮窗权限；Android 13+通知权限不足时先走权限申请。系统共享取消或失败不建立假运行会话。
2. `VisionRuntime` 在固定识别线程预热/复用本机模型；`ProjectionConsentRequest` 按系统选择范围：API37+ APP_TASK，旧系统 DISPLAY；BETA仍要求受支持的单应用系统。正式身份与采集能力分别由两个BuildConfig标志控制。
3. `CaptureService` 建立前台服务、独立采集接收端和悬浮条；会话代次 `generation`、可见性 `epoch`、接收端尺寸及所有权共同约束输入。APP_TASK必须确认任务尺寸后才接受对应像素。
4. 最新帧经 `TencentRecognizer` 形成模型检测、场景/数量OCR和几何归属，再交 `RoundObserver`；花色/级牌是协作的旁路，不能阻塞所有普通事件。
5. 正常运行主按钮为停止；停止请求是异步的，可显示“正在停止…”。`CaptureLifecycle`/`CaptureCleanup` 幂等释放reader、virtual display、projection、worker、overlay和通知，个别释放失败不跳过其他项。

按Home暂退不等于移除任务；真正最近任务移除、显式停止、系统投影停止等走清理。旧会话回调、旧epoch分析和已关闭的异步保存不能启动新会话或改新局。

### 识别管线的入口

当前已提升能力开启时，`DetectionPipelinePolicy`选择FULL_CPU，不读取旧reference资格来切换生产路径。`LocalCardDetector.kt`的FULL模型为本机`app/src/main/assets/models/cards.tflite`，按固定SHA-256校验，输入形状为1×640×1280×3、输出1×32×16800；CPU使用4线程和XNNPACK。PACKED与GPU实现/实验入口仍在源码，但存在代码不等于当前生产选择它们；尤其GPU构造可能停滞，不能为了省电未经验证自动切换。

FULL检测将原图等比letterbox到输入画布、黑色补边，RGB除以255转float；解码每个锚点的28类最大分，低于0.55不进入候选，坐标再映回原图归一化槽位。候选按分数排序，IoU大于0.45的重叠框抑制。仅当原尺寸和**完整模型输入像素**均相同才复用上次检测，不用感知hash或局部抽样判断画面未变；新采集仍须经过观察、时间和事件边界校验，复用推理不等于已记过这一手。

检测结果仍须经过手牌分区、整组座位归属、区域可观察性和场景/OCR交叉检查，再生成`TableFrame`。`SceneOcr`异步来源及数量专属像素必须保持采集时间，不能把晚到回调冒充新一帧。`EmptyRegionGuard`/`TencentFrameVisibility`等适配器区分真正可见空区与未见区域；黑块、局部遮挡、调设置和模型未出框都不自动等于“不出”。这些步骤的布局/阈值改动必须用原图级证据验证，旧tape回放不会重新执行模型。

## 3. 场景、账本、展示是三套状态

`TableScene` 包含 TABLE、DEALING、LOBBY、TRIBUTE、TEAMMATE、RESULT、UNKNOWN。它是图像解释结果，**不是**持久账本阶段。DEALING/TRIBUTE是开局基线取证窗口，进贡还贡不记作普通出牌。

`RoundPhase` 的实际枚举和转换如下；旧PRD中的REVALIDATING、ROUND_UNAVAILABLE、CAPTURE_LOST等是历史设计概念，不应凭名称新建第二套运行状态。

| 账本阶段 | 进入/退出 | 数据语义 |
| --- | --- | --- |
| WAITING | 新会话或`waitForNext()`；经合格27张完整初手`begin()`进入ACTIVE | 无本局精确池；等完整开局，不猜中途历史 |
| ACTIVE | 已确认初手及当前事件；本手清空进入SELF_FINISHED，真实缺口进入RECOVERING | 正常原子提交；其他座位可独立处理 |
| SELF_FINISHED | 本人确已出完，可能展示队友牌 | 三家仍可记；只允许受限的迟到自己末手事务，不把队友当新自手 |
| RECOVERING | `suspendForRecovery`保存原ACTIVE/SELF_FINISHED检查点 | 原历史不删，raw `remaining=null`；有证明的`resumeAfterRecovery`原子恢复原阶段 |
| UNAVAILABLE | 显式`invalidate`，不是普通弱读的通用出口 | 不提供当前精确池；不得靠重置历史假恢复 |
| FINISHED | 独立足够结束证据或结果边界 | 结束不等于核实成功；残留reason/pending保持未核实，之后清到WAITING |

`ConfirmedRoundPresentation` 另保存同局可显示的确认快照。局中局部待确认、真实断点或队友牌池重验时可暂留旧数字/历史，后台仍记录真正待确认状态；停止、未准备好、新局/明确边界清缓存。这样不闪问号也不展示常驻复核页，但不能因此把旧数字称为“本帧已核准”。

## 4. 基线、事件和未知池

标准牌库108张，初手27张。`RoundLedger.begin`校验完整张数和容量，**同局初手不可变**。普通牌精确同点同花最多2张，同点同颜色最多4张，同点总数最多8张；大小王各2张。显示牌序只影响布局，不改变容量和牌型规则。

```text
raw未知池 = 完整牌库 − 自己已确认初手 − 三家成功提交的已出牌
显示未知池 = raw未知池 − 当前版本已确认的队友余牌（如适用）
```

此处公式是主账本按Rank聚合的计数投影，不是已经精确确认四花色的逐张物理牌集合。桌面变牌可能按替代点数展示，实体花色和替代身份另由旁路约束；不能把该聚合计数直接当成物理牌证明。

自家出牌仅从当前自手扣，不再次减raw未知池。三家数量和详情来自同一份`PlayEvent`列表，详情不出不记、JJ为两张J、手间以`·`分隔。

`RoundLedger.commit`检查局ID、事件唯一性、序号单调、容量、自手差分和每家≤27。完全相同的同ID事件是幂等重送；同ID不同内容或旧序号拒绝，拒绝不产生半次扣牌。动画补齐只能在同一最新观测事件上严格扩展；不能为了凑数任意改写早先事件。

## 5. 直接观测到提交：证明家族

普通多帧候选要求点数/颜色/槽位、观察连续性及新事件边界相容。`Vote`对相同时间不重复计票，普通外家候选与初手有不同阈值；快路径仍需独立强证据，不是把全局阈值调低。具体常量以对应实现和测试为准，不把一条“四帧”规则套所有路径。

| 实现入口（core） | 主要处理什么 | 不能放宽的边界 |
| --- | --- | --- |
| `Observation.kt`的普通候选/Presentation | 同槽停留、返回帧、新一手及旧手动画扩展 | 空像素/遮挡不是清牌证明，不能仅字符串去重 |
| `QuantityAnchoredPlayProof.kt` | 直接牌组+独立余牌数量锚定 | 数量只确认已看见的牌组，不生成牌面 |
| `RepeatedPlayCountProof.kt`、`RepeatedSingleCardProof.kt`、`CountAnchoredRepeatedSingleProof.kt` | 两手同值或重复单张，避免停留和新手混淆 | 新边界与来源必须成立，不重扣同一显示 |
| `PassClosedSupersetProof.kt` | 过牌关闭旧动作后出现严格超集的新手 | 过牌不能证明旧像素为空，固定期限及原锚点不能被噪声续命 |
| `UntrackedSeatReview.kt` | 单家已见、尚不能确定扩展还是新手的有限journal | 不丢早先未知组去只记后面一组；不封锁无关座位 |
| `LocalizedPendingPlayRecovery.kt` | 明确局部遮挡前后的有限恢复 | 确认其他锚点和未变自手，不能泛化成全局历史重建 |
| `OwnExitPlayProof.kt`、`OwnHandDifferenceProof.kt`、`OwnDelayedHandDifferenceProof.kt`、`TerminalOwnHandProof.kt` | 自己离手差分、交接、迟到末手 | 原手与SELF事件版本不变；只提交已直接证明的实际最后一手 |
| `EarlyFinishPlayProof.kt`、`TerminalSeatPlayProof.kt` | 头/二游和终局动画中的最后牌 | 自动三游、尾家揭示剩牌不算实际已出 |
| `TeammateHandPlayProof.kt` | 本人出完后，通过完整队友展示变化证明其后续出牌 | 只针对OPPOSITE，对家事件版本匹配；不能把整副展示追加成一手 |

需要确认消费的proof统一遵守：**observe提出提案→调用账本事务→成功后对相同提案`commitAccepted`**。失败不提前消费，后续可纠正后重试；新观察/清理能撤销旧提案，不能拿过期对象补交。普通弱读只使临时票数失效；完整证书、固定到期时间、已消费状态分别管理。

### 独立数量的来源

`TencentRemainingCountSource` 复用OCR快照，要求横屏、尺寸一致、原来源年龄≤1秒、定位的剩余数量专属像素、金色底板及mask校验；`TencentRemainingCounts`按三家固定位置映射，冲突数量不采信。重复/同源矛盾/逆序OCR不能增加票数，不能用较晚回调时间刷新旧来源。账本推导的`remainingHands`不具备这一独立性。

## 6. 局部不确定与真实输入缺口

| 情况 | 处理 | 何时重新计入 |
| --- | --- | --- |
| 单帧弱读、残缺、某次数量噪声 | 丢本帧票数，保留合法历史和固定期限 | 重新取得足够新且独立的证据 |
| 合法账本拒绝某次候选 | 拒绝本次提案，记录拒绝计数，其他座位继续 | 正确候选通过完整事务；成功才消费proof |
| 单家新手/扩展无法区分 | 单家journal和待确认状态，其他家/自己独立处理 | 直接牌面、边界、独立数量解释唯一 |
| 整个任务不可见、真实尺寸/像素连续性中断 | 采集层`CaptureGapFence`先排队断点并隔离旧源帧；观察层保留账本检查点进入恢复 | 只能接受检查点锚定的有证据重连/扩展/追加；不能忽略中间未知历史 |

`CaptureGapFence`的pending即使已被消费者取走，源时间截止仍保留，拒收故障时刻及之前的迟到帧。两次缺口之间不能拼接临时几何票数。generation/owner清理只属于对应采集会话。

单应用输入接收端修复在原投影上有限重接，不复用token建立第二个会话。`TaskResumeRecoveryPolicy`要求真实可见性/尺寸断点、同局同epoch和新鲜输入资格；最多2次会话请求，空内容持续、冷却和请求期限均有界。它修接收端，**不会修出从未看到的牌**。普通模型弱读不授予无限重启权。

## 7. 自己出完、队友剔除和终局

自己完成提示与末手实际牌面可能不同步。受限`commitLateOwnExit`校验完整原手、SELF历史版本、新序号及当前局后原子补交；失败整体回退，不改变外家已确认事件。

`RemainingPoolTracker`要求SELF_FINISHED、队友完整余牌数恰等于`27−对家已出`、容量相容；同一局/epoch/对家事件版本下至少3次稳定观察且跨度≥500ms后才发布排除。它只做显示/分析投影，不修改本人初手或把队友余牌记作出牌。

后续队友真实单张可按颜色身份安全减去；若同色有不同花色可选，则降低为颜色不确定。多张展示可能有变牌替代，需要重新取得完整队友余牌；版本失配先撤回/重验投影，确认显示暂留旧范围，防止回退到混合三家池导致同花顺一瞬变黄。

整局结束需足够的完成/结果证据。`confirmedRoundFinished`使用已确认出完组合，双方双出及其他完整结束条件与自动排名不同。终局仍有journal或被拒的末手，`finishLedger`保留未核实状态；FINISHED不能洗掉此前reason。新局清候选、事件锚点、数量来源、队友投影、级牌、同花顺和显示缓存，不能沿用旧局证据。

## 8. 级牌、实体牌及同花顺

`GradeSourceReader`、`RoundGradeTracker`读取当局彩色HUD、开局来源及合格牌角，暂时失败不撤回同局确认级牌；灰色另一方、场名文字或上一局缓存不构成当前规则。精确♥计数与普通级牌列是同一事务，由`GradeCounterPresentation`保持确认值，避免半新半旧双问号。

红桃级牌是实际物理逢人配；单出按原级牌。桌面可能把它显示成替代点数，证据跟踪器用实体槽位/颜色/花色及规则约束保留所有可行分配，不能直接把显示目标当真实消耗，也不能把已用变牌重复用于补两个位置。

`StraightFlush`枚举4花色×10个恰好5张窗口：A2345…10JQKA，A不跨中间；级牌在顺序中按原点数。每个窗口结合剩余天然实体、仍可用逢人配、未知花色分配和每家余牌容量搜索。自己初手已排除；确认队友余牌后目标缩到对手。每家不足5张可直接排除，不因整池凑够5张就认为某家一定有。

| 原始分析结果 | 含义 | 显示处理 |
| --- | --- | --- |
| POSSIBLE | 当前计算范围内有可行构造 | 图案亮，候选普通点数金字；不证明某家实际持有 |
| IMPOSSIBLE | 当前证据与规则范围的所有分配均已排除 | 图案暗、相应候选白字；不外推到未知规则之外 |
| UNKNOWN | 证据不足、分配冲突或规则/替代身份待确认 | 通常保持本局同范围最近确认显示；有界候选上界严格收窄时也可更新 |

**未知级牌“只算天然”是构造证据的范围，不是把未知变牌当不存在。** 未确认规则时，确定可行证明不主动使用假定逢人配；未知替代仍可扩大候选上界、留下UNKNOWN。NATURAL_ONLY的排除不是“任何可能规则下含变牌都绝无同花顺”。不显示“未识别级牌”提示，不等于删除内部未知状态。

`StraightFlushPresentation`按局ID、规则范围和队友牌池处理缓存。UNKNOWN一般不覆盖旧确认；不将暗色永久锁死，规则变化/新局清理；图案与点数字共用同份发布结果。花色旁路最多每250ms取有界ROI（总≤400,000像素），异步结果必须仍匹配当前会话/局/epoch/事件版本。

## 9. 配置、页面、手势与默认值

`ConfigStore`用SharedPreferences `jpq-display` 的`config`保存；旧字段缺失用默认值，非法整体读入回退默认。导入schema1、≤32KiB，先decode/validate再save，失败不覆盖；不是任意schema自动迁移框架。

| 八项尺寸参数 | 默认值 | 校验范围 |
| --- | --- | --- |
| widthScale | 1.01191494 | 0.8–1.35 |
| gridRatio | 0.42402228 | 0.3–0.6 |
| gridHeight | 0.94622684 | 0.85–1.3 |
| recordHeight | 0.98167837 | 0.85–1.3 |
| headerText | 0.89647275 | 0.8–1.35 |
| valueText | 0.96344686 | 0.8–1.35 |
| counterText | 1.0216086 | 0.8–1.35 |
| detailText | 0.90082836 | 0.8–1.35 |

默认显示三家+详情、重置、同花顺和级牌提示，双击隐藏关闭；默认牌序大、小、A…3、2。15牌种必须唯一完整，♥为独立展示投影而不是第16种可重排Rank。位置归一化0–1，旧位置兼容由位置记忆层处理。

开关/三家模式保存后刷新；尺寸与牌序使用草稿，只改预览，保存并退出才生效，直接退出丢弃草稿。运行中保存可通知条刷新，但切去设置导致真实采集缺口仍按输入规则处理。权限系统返回会重绘复查，不自动开始记牌；页面返回按进入来源。

拖动超过touch slop即可开始，不必须先长按；长按消费点击但不弹面板。隐藏态显示按钮同样可拖；手势结束保存位置，拖动不误触显示。`HistoryWidth`保存基础尺寸，运行中按真实文字宽度扩展只涨不缩，不将扩展宽度写回设置；详情、仅数量、无三家采用不同宽度分支。

## 10. 线程、保存与诊断

| 所有者 | 工作 | 隔离要求 |
| --- | --- | --- |
| UI主线程 | 页面、悬浮绘制、权限/系统安装入口 | 不做模型推理或长时间导出，显示不是证据源 |
| 采集HandlerThread | ImageReader到有界CapturedFrame | Image不跨线程；只发布最新帧，旧所有权必须释放 |
| `VisionRuntime`固定线程 | 模型/OCR适配、观察者协调 | 模型在同一线程使用/释放；sessionGuard不能包住耗时推理 |
| `StraightFlushAnalyzer`单线程 | 花色/规则实体旁路 | 复制有界ROI、busy节流、不堆积，结果核对版本 |
| `AsyncRoundStore`/证据保存线程 | 本机SQLite及诊断写入 | 只传拥有副本，慢IO不持采集会话锁 |
| `EvidenceWork`维护互斥 | 导出/清理 | 要求已停采集且退休写线程结束；不从正在写的目录任意压缩/删除 |

`RoundRepository`是SQLite `rounds.db` v2，`rounds`保存结构化状态、`suit_evidence`独立保存注释；1→2增加表而非清库。保存按最近触碰最多21条，最近列表显示20条；这不是用户可任意修改的牌库。

`VisionRuntime`在停止使用约120秒后尝试释放模型；若仍在记牌则不释放，GPU且屏幕非交互时继续延后。它与花色节流、有界最新帧分别解决资源寿命/排队问题，不能据此宣称所有设备已经低功耗或达到温升目标。

诊断默认关闭，`SessionTrace`在新会话建立时读取开关，运行中切换不会改当前会话；关闭不删除旧文件。画面100MiB、会话目录64MiB、采集探针256MiB是不同保留上限；trace每文件默认8MiB、当前+6个轮转。导出/清理需停止并等证据写完，清理涉及数据库及`sessions`、`diagnostic`、`capture-probes`，不是普通退出自动删除。

识别不依赖网络；联网只作正式更新。隐私资产和诊断不提交Git、不上传Cloudflare。

## 11. 更新行、下载和安装

| 状态 | 一级更新行右按钮 | 实际动作 |
| --- | --- | --- |
| BETA / 记牌中 | BETA / 记牌中，禁用 | 不读装正式通道、不在对局发起安装 |
| 检查/下载/安装校验中 | 检查中／下载百分比／校验中，禁用 | 有界异步任务，不创建重复所有者 |
| 需重新查 / 无更高版本 | 检查更新 | 手动可绕过每日节流，重新验证签名清单 |
| 已知更高版本但无完整有效包 | 下载 | 非Wi-Fi时需用户确认，绑定当前签名清单恢复或重下 |
| 同一版本包已验证 | 安装 | 后台再核身份/字节，交系统确认；不是静默安装 |

非手动清单检查按24小时节流；已有合法pending不会因日限额而失去下载调度。检查Job要求有网；自动下载Job要求**非计量网络**且记牌停止，配延迟/退避。它不要求设备系统idle，非计量也不限于Wi-Fi。文档所说“空闲”指不在记牌会话，不是`setRequiresDeviceIdle`。

部分文件与签名清单绑定，用Range及ETag/Content-Range验证续传；清单切换或响应不符不拼包。整包SHA、大小、包名、versionCode/versionName、minSdk、安装证书都验证后才允许安装；安装所有权还绑定同一文件快照，避免校验后文件被替换。安装失败不卸载旧版或清配置。

更新清单规范与部署见 [契约](../design/update-contract.md)、[服务说明](../../services/updates/README.md)。用户意向中的暂停/继续专页、任意schema迁移等早期提案，不能因旧PRD有文字就说当前已实现。

## 12. 新会话修改时怎么使用本文

需求对应编号→当前规格→本手册责任模块→源码与测试。修恢复要同时验证正常事件、拒绝事务、重复/矛盾来源、局部与真实缺口组合、自己末手/队友、终局未核实和跨局清理；修UI不应改账本证据。改变实际语义时同步修改本手册、需求追踪及当前规格，不能只在旧修复报告追加一句。

本次可确认的是文档与上述代码入口已对照；本手册不是新增模型/手机/实战准确率证明。当前验证与缺口始终以正式发布记录及保留原始证据为准。
