# 单应用采集与发热耗电研究

日期：2026-10-19。对象：稳定基线 `v0.2.26` / `ea55681`。本轮仅检查代码、既有实验和已有日志，查阅官方文档；没有安装、操作手机、改生产代码、切换配置或发布更新。

## 结论

1. 单应用 MediaProjection 是解决外部浮窗/通知污染采集的优先方向。已有本机专用测试的阳性/排除对照成功，但尚未证明真实大掼蛋及各种澎湃窗口类别都通过。
2. 可以研究减少额外开销，先处理诊断对象构造、无效图像复制，再验证区域打包识别或硬件后端。暂无电量/温度 A/B，不能给节电百分比或承诺无损。
3. 两项分开验证，不把采集范围变更、坐标改造、识别加速和降帧混成一次无法归因的大改动。稳定版本保持原样。

## 1. 单应用采集

### 官方机制

Android 的 app screen sharing 共享所选应用内容，不合成状态栏、导航栏、通知等系统 UI。Android 14 QPR2 引入这一功能；系统共享授权由用户选择，每个新会话须重新同意，授权只供一次创建 VirtualDisplay。尺寸变化应 resize 原显示/Surface，处理内容可见性及停止回调。依据：[单应用共享](https://developer.android.com/about/versions/14/features/app-screen-sharing)、[MediaProjection 指南](https://developer.android.com/media/grow/media-projection)。

API 37 的 `MediaProjectionConfig.Builder` 可配置授权界面提供的来源类型和初选来源，因此已测 Android 17 手机还可评估只提供 APP 来源，减少误选整屏。选哪个应用仍由用户选择，不是代码偷偷指定包名。当前工程 compileSdk 36，使用该新增 API 需要另行升级编译 SDK 并做版本分支，不能仅凭手机 API 37 就直接调用。[Builder 官方说明](https://developer.android.com/reference/android/media/projection/MediaProjectionConfig.Builder)。旧支持系统可走 `createConfigForUserChoice()`，不把旧整屏限制当作系统没有能力。

### 本地已取得证据

`docs/development/scope-probe-20261015.md` 记录：

| 对照 | 系统实际范围 | 合格帧 | 独立 UID 不透明悬浮窗覆盖处 |
| --- | --- | ---: | --- |
| 整屏 | RECORD_CONTENT_DISPLAY / display0 | 52 | 采集到合成洋红 `(204,51,204)` |
| 单测试应用 | RECORD_CONTENT_TASK / 测试包 UID | 58 | 仍是底图绿色 `(0,255,0)` |

两次都有独立实际屏幕截图，证明手机上确实存在浮窗；横屏→竖屏→横屏分别取得稳定、时间递增的多帧。故不能继续笼统称“这项实验失败”。此前未接入是用户当时选择保持原交互。原始失败记录、最终成功证据和临时状态恢复均保留。

这个结果仅证明当时系统、测试任务与一种外部 TYPE_APPLICATION_OVERLAY 的隔离，不证明真实游戏、所有通知/权限窗/画中画、全部手机系统或永久无漏帧。

### 当前代码为什么仍受遮挡

- `MainActivity.requestProjection()` 在 API 34+ 显式 `createConfigForDefaultDisplay()`，生产仍请求整屏。
- `CaptureService.newReader()` 按物理屏幕和 reference 固定横屏画布建立采集；回调没有形成独立的 task 内容坐标模型。
- `CaptureFrameProducer` 将条、调整页、级牌提示的物理屏幕矩形投到采集图中涂灰，后续 `TencentFrameVisibility`、`GradeSourceReader` 把这些位置视为被遮。
- 仅改系统授权而继续涂这些矩形，会把系统已经提供的完整游戏像素再次盖掉，因此必须同步改采集范围和遮挡语义。

### 推荐接入方案（待开发）

开始记牌 → 系统选择仅共享应用 → 选择大掼蛋 → 原悬浮条照常显示，可跨多局使用。新采集会话再次授权，取消/选错/游戏未就绪有明确出口。可保留整屏兼容分支，不在静默失败后偷偷切换范围。

正式实现需要独立记录：期望范围、实际内容验证状态、内容尺寸与 epoch、物理屏幕几何。API 37 可研究来源选择限制；不能依赖只有 ADB dumpsys 才可读取的字段来实现生产验证，也不能仅以宽高相同断言已选游戏。

单应用流应以真实 task 内容重算区域、旋转/Insets/letterbox。**确认外部 overlay 确实不在输入后，不再将它的物理位置作为游戏遮挡 mask；**物理条位置仅用于屏幕布局。整屏流继续现有 mask/提醒；范围不明时保守处理，不能直接删掉所有遮挡保护。游戏自己绘制的弹窗、动画、黑屏或暂停仍属于输入问题。

单应用模式确认隔离后，原级牌遮挡提示对外部条不再有意义；只在整屏兼容模式保留。这是新模式的设计推导，未修改当前设置行为。

### 验证顺序

1. 在非对局的真实大厅或静态规则页，对照实际屏幕和采集输入：自家条覆盖级牌、规则文字等可定位内容，输入仍包含被盖的原游戏内容。
2. 分别覆盖聊天小窗、多个外部浮窗、通知横幅/通知栏、系统提示/通话、画中画，记录是否排除、是否暂停游戏渲染或触发可见性变化；不把一种窗口通过推及全部。
3. 校验横竖切换、task resize、内容不可见/恢复、共享取消/停止/重启、锁屏、退出游戏。只创建一次 VirtualDisplay，结束仍完整清理。
4. 完成图像/OCR/区域回放后，用户正常打完整局；真实对局期间不加第二份共享、不做对照截图或 instrumentation。只用 APP 本地诊断和只读日志，结束后核对事件连续性。

目标是排除外部遮挡导致的输入污染；这不保证游戏自身被系统暂停、内部弹窗或真实漏采集时也能凭空获得牌面。

## 2. 发热与耗电

### 已有测量说明什么

最新三局 session `1792379535565-11129492`，已有 trace-summary 与原 trace 交叉核对：

| 项目 | 结果 |
| --- | --- |
| frame 总数 / 有模型字段 | 3,749 / 3,647 |
| 实际 profile / backend | 3,647 帧均 FULL / CPU |
| 完整输入相同缓存 | 475 命中、3,172 未命中（有字段帧约 13.0% 命中） |
| 观测帧间隔 | 中位 199ms，P95 282ms |
| 图像转换 | 中位 7ms，P95 13ms |
| 模型预处理 | 中位 9ms，P95 13ms |
| 推理 | 中位 175ms，P95 238ms |
| 解码 | 中位 1ms，P95 2ms |

这些是已有测试、开启诊断时的阶段耗时，不能换算为电量份额。日志没有同时测电流、累计电荷或温升；游戏本身、亮度、充电、环境和其他浮窗也消耗功率。

当前 `FULL` 模型输入 1280×640，CPU 4 线程 XNNPACK。已有 reference 区域打包 640 模型实现，但本次实际日志没有使用它，不能将代码存在当作已享受加速。GPU 构造曾在支持手机上卡住，生产固定 CPU；NPU 路径尚未实现。

采集 gate 最短 33ms，理论最多约 30 次/秒进行转换；实际模型观测约每 200ms 一次，不能说“完整识别跑在 30FPS”。`LatestFrameDispatcher` 仅保留最新待处理帧，替换的帧可能已经做过全幅复制，值得研究提前减少这类无效工作。2608×1200 的 RGBA 单帧约 12.5MB，此数是数据体积，不是实测功耗。

### 已做的优化

- Bitmap/DirectBuffer/像素数组/张量和有界池复用，图像转换批量拷贝。
- 完整模型输入逐像素完全相同才复用结果；新采集时间仍参与证据检查，不用感知 hash 把相似牌面当相同。
- OCR 至少 250ms、单任务；花色/同花顺 offer 至少 250ms、busy 限流。
- 同花顺证据的 SQLite checkpoint 内容改变才写盘；显示状态改变才通知 UI。悬浮窗并非每采集帧无条件重绘。

### 优化优先级

| 方向 | 研究结论与条件 |
| --- | --- |
| 日常关闭完整诊断 | 现成开关，默认关闭；会停额外 JPEG、完整 trace 写盘/日志，不改变识别。当前手机开关状态本轮未读取，不擅自更改 |
| 诊断对象懒构造 | 优先候选：`TencentRecognizer` 无条件创建每帧大 JSON 再调用 `SessionTrace.write`，enabled 判断在 write 内；关闭时仍有分配/列表遍历成本。把诊断构造放入受控入口，业务证据运算保持，验证开启/关闭账本一致 |
| 更少无效转换/复制 | 研究背压/最新帧调度，把会被覆盖丢弃的重转换尽量延后；保留输入新鲜度和当前有效证据频率。不能简单忙时长时间不取图，导致新帧过时 |
| 区域打包识别 | 查 qualification 未启用原因，用现有 packed640 和全图兜底验证覆盖。测所有牌区/高牌堆/队友视角/变牌/级牌，统计兜底率和双推理总成本，通过后才启用 |
| GPU/NPU 或 CPU 线程数 | 独立长时 A/B。加速器可能节能，也有同步/兼容、数值差异和与游戏争 GPU 风险；现有 GPU 卡住先解决，不直接打开。减少线程也可能延时更长、总能耗更高 |
| 更低分辨率、量化、降 OCR/推理频率 | 不作为首批无损优化。可能丢细小花色、短暂末手、重复同牌边界；需独立准确性与延迟验证，不能只看剩余数量守恒 |

Google 官方说明硬件 delegate 有加速/能效潜力，但可能因精度和 CPU/GPU 分割同步改变结果或速度，需基准测量。[Delegate 评估](https://developers.google.com/edge/litert/performance/delegates)、[GPU 支持与限制](https://developers.google.com/edge/litert/performance/gpu)。

单应用采集排除浮窗后，可能提高相同输入缓存命中、减少遮挡复核；游戏自身动画仍改变输入，不能提前承诺明显省电。

### 功耗验收计划

比较游戏单开、游戏加采集、游戏加完整稳定记牌、候选优化记牌；诊断关闭和开启单独成组。固定亮度/刷新率、网络、起始温度和环境，尽量在断开充电的相同条件下重复，记录长时累计电荷/能量、温升、CPU 活跃与频率、转换/推理次数和延迟。电池温度不等于 CPU/GPU 温度。

使用同一份连续素材做识别 A/B，验证事件、座位、物理牌和花色、同花顺、队友剔除及末手恢复；再做真实游戏共负载测试，确认长时温控后仍不漏记，P95 扣牌延迟无实质退步。性能采样不能引入另一份屏幕投影，也不以显示缓存掩盖未记账。

Android Studio ODPM 电源轨不能默认认为小米可用；官方主要列 Pixel 6+。其他设备可研究电池电荷/电流读数和 System Trace，但这是整机数据，需通过受控 A/B 估计额外开销，不冒充精确 APP 独占功耗。[Power Profiler](https://developer.android.com/studio/profile/power-profiler)、[System Trace](https://developer.android.com/studio/profile/cpu-profiler)。

## 推荐下一步

先建立独立候选分支，做真实大掼蛋单应用采集的非对局像素对照，确认隔离及内容坐标后再接入；节能先做不参与识别结果的诊断懒构造。随后依据功耗与延迟基准选择打包路径/硬件后端。两条线路分别验证，均通过后再打完整候选包，不改动 `v0.2.26` 标签。
